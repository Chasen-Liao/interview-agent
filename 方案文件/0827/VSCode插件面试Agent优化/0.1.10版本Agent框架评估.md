# Interview Agent 0.1.10 Agent 框架评估

日期：2026-08-30

## 1. 结论

当前阶段不建议把正式运行链路从自研 Agent 循环迁移到 LangChain、AutoGen 或 AgentScope。

原因：

1. 当前核心链路是单 Agent 面试官 + OpenAI 兼容 tool calling，现有 [agent_loop.py](../../../agent/agent_loop.py) 已覆盖模型调用、工具执行、历史压缩、流式输出、取消和最大步数安全阀。
2. 0.1.10 同时要优化 VSIX 体积，引入任一主流框架都会增加 Python 依赖、安装时间和排障成本。
3. 当前更缺的是 OCR 反馈、上传稳定性、包体积和可观测性，不是多 Agent 编排。

建议：0.1.10 保留原生 runtime；0.1.11 之后如果工具编排继续复杂，再做 LangChain / LangGraph PoC。

## 2. 当前循环职责

| 职责 | 当前位置 | 后续迁移边界 |
|---|---|---|
| 模型调用 | [llm_client.py](../../../agent/llm_client.py) | 第三方框架只能替换调用编排，不应替换 VS Code 配置读取 |
| 工具 schema | [tools/base.py](../../../agent/tools/base.py) | 需要能转换为框架工具定义 |
| 工具执行 | [agent_loop.py](../../../agent/agent_loop.py)、[tools/builtin.py](../../../agent/tools/builtin.py) | 工具实现继续复用，不重写业务工具 |
| 历史压缩 | [history.py](../../../agent/history.py) | 迁移后仍需保持 token 上限和最近工具结果保留策略 |
| 流式输出 | [llm_client.py](../../../agent/llm_client.py)、[protocol.py](../../../agent/protocol.py) | 必须继续支持 Webview 打字机输出 |
| 取消 | [agent_loop.py](../../../agent/agent_loop.py)、[main.py](../../../agent/main.py) | 框架 runtime 必须能在工具调用前后响应 stop |
| 会话落盘 | [session.py](../../../agent/session.py) | 不随框架迁移改变文件格式 |

## 3. Runtime 接口草案

先按文档边界约束，不在 0.1.10 落代码。

```python
class AgentRuntime:
    def run(
        self,
        user_text: str,
        on_tool_call: ToolCallCallback | None = None,
        on_response: ResponseCallback | None = None,
        on_delta: ResponseCallback | None = None,
        should_cancel: CancelCallback | None = None,
    ) -> str:
        ...
```

约束：

1. 输入输出兼容当前 `AgentLoop.run()`。
2. 工具通知格式不变，Webview 不因 runtime 替换而修改。
3. 历史消息仍由 session 管理，避免迁移破坏历史恢复。
4. 第三方框架只作为 runtime 实现，不进入 VS Code Host。

## 4. 框架对比

参考资料：

1. [LangChain Python Agents](https://docs.langchain.com/oss/python/langchain/overview)
2. [Microsoft AutoGen Stable Docs](https://microsoft.github.io/autogen/stable/)
3. [AgentScope 中文文档](https://doc.agentscope.io/zh_CN/)

| 框架 | 适合当前项目的点 | 不适合点 | 迁移优先级 |
|---|---|---|---|
| LangChain / LangGraph | 单 Agent、工具调用、middleware、后续工作流编排 | 需要适配当前消息历史、OpenAI 兼容 baseUrl、流式工具通知 | 高，适合先做 PoC |
| AutoGen | 多 Agent 团队、事件驱动、GraphFlow | 当前不是多 Agent 产品，异步和团队编排会显著增加复杂度 | 低，等多面试官方向再评估 |
| AgentScope | 中文文档、ReActAgent、多智能体、Tracing / Studio | 对当前本地 VS Code 插件交付偏重，依赖与冷启动要实测 | 中低，可做中文生态观察 |

## 5. PoC 设计

PoC 不进入正式包，不写入 `pyproject.toml` 运行依赖，不打进 VSIX。

统一输入：

```text
我做了一个基于 Redis 和 MySQL 的后端项目，请读取项目结构并追问一个技术问题。
```

统一工具：

1. `list_directory`
2. `read_file`
3. `search_code`

统一指标：

| 指标 | 通过标准 |
|---|---|
| 依赖大小 | 安装后新增依赖可解释，不影响基础 VSIX |
| 冷启动时间 | 不明显慢于当前原生 runtime |
| 首 token 时间 | 支持流式输出，且 Webview 可接收 |
| 工具调用成功率 | 三个工具 schema 均能稳定调用 |
| 取消能力 | stop 后能尽快停止下一步模型或工具 |
| 改动量 | 不改 VS Code Host 和 Webview 协议 |

退出条件：

1. 无法复用现有 OpenAI 兼容配置。
2. 无法稳定流式输出。
3. 工具调用通知不能映射到当前思考球详情。
4. 引入依赖导致包体积或安装时间明显失控。

## 6. 后续建议

1. 0.1.11 如继续做框架方向，先做 LangChain / LangGraph PoC，因为它最接近当前单 Agent 工具循环。
2. AutoGen 留给多角色面试官、评分员、总结员协作场景。
3. AgentScope 留给中文多智能体和可视化调试评估，不作为当前默认迁移目标。
