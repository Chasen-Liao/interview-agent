# Interview Agent 0.1.9 OCR 处理优化开发任务清单

调研日期：2026-08-30

## 1. 本版本目标

0.1.9 只聚焦 OCR 处理质量和速度，不扩展为完整文档理解系统。

目标：

1. 确认并接入更适合当前项目的轻便开源 OCR 方案。
2. OCR 入口支持传入扫描版 PDF 和图片文件进行识别验证。
3. 建立可重复的 OCR 质量和耗时测试，避免只靠人工观感判断。
4. 保持 OCR 依赖可选，不拖慢普通 PDF、DOCX、TXT、MD 简历上传。
5. 修正当前 OCR 包接入形态和最新 RapidOCR 生态之间的差异。

暂不做：

1. 不做云 OCR，不上传简历到第三方服务。
2. 不做表格结构化、版面还原、PDF 转 Markdown。
3. 不做 GPU 专用加速路径。
4. 不默认安装 OCR 重依赖，仍由用户按需安装。

## 2. 当前 OCR 状态

| 项目 | 当前状态 | 问题 |
|---|---|---|
| OCR 入口 | [resume_ocr.py](../../../agent/resume_ocr.py) | 只面向 PDF，图片不能直接作为 OCR 输入 |
| OCR 引擎 | 当前使用 `rapidocr-onnxruntime` 的 `RapidOCR` | RapidOCR 主仓库当前推荐 `rapidocr + onnxruntime`，包名和导入方式已有变化 |
| PDF 渲染 | 使用 PyMuPDF 将前 5 页渲染为图像 | 没有可配置 DPI / 页数 / 超时基准 |
| 图片处理 | 无直接图片 OCR 路径 | 无法按用户要求用图片对 OCR 接入做真实测试 |
| 自动测试 | TS 层已有 PDF 文字层为空时触发 OCR fallback 的测试 | 缺少真实 OCR 引擎对 PDF / 图片的集成测试 |
| 依赖安装 | [pyproject.toml](../../../pyproject.toml) 和 [prepare-agent.js](../../../vscode-extension/scripts/prepare-agent.js) 生成 OCR 可选依赖 | 仍使用旧 `rapidocr-onnxruntime` 依赖清单 |

## 3. 开源 OCR 项目调研结论

优先结论：0.1.9 推荐以 **RapidOCR 当前主包 `rapidocr + onnxruntime`** 作为首选方案，并保留对旧 `rapidocr_onnxruntime` 导入的短期兼容判断。理由是当前项目已经按 RapidOCR 思路实现了 PDF fallback，迁移成本最低；同时 RapidOCR 官方定位为开源、本地、多平台、多语言、快速离线部署，默认支持中英文，符合简历 OCR 场景。

| 项目 | 地址 | 适配判断 | 0.1.9 建议 |
|---|---|---|---|
| RapidOCR | [RapidAI/RapidOCR](https://github.com/rapidai/rapidocr) | 官方说明支持多平台、多语言、快速离线部署，默认中英文；安装示例为 `pip install rapidocr onnxruntime` | **首选接入**，先用新包基准测试，再决定是否替换旧包 |
| rapidocr-onnxruntime | [PyPI rapidocr-onnxruntime](https://pypi.org/project/rapidocr-onnxruntime/) | 当前项目已使用；最新 PyPI 版本 1.4.4 发布于 2025-01-17，要求 Python `<3.13` | 作为兼容方案，不再作为长期首选 |
| rapidocr-pdf | [PyPI rapidocr-pdf](https://pypi.org/project/rapidocr-pdf/) | 包很小，面向 PDF 内容提取，但项目现有 PyMuPDF 渲染逻辑已经足够短 | 暂不引入，除非真实测试明显减少代码并提升速度 |
| OCRmyPDF | [ocrmypdf/OCRmyPDF](https://github.com/ocrmypdf/OCRmyPDF) | PDF 能力成熟，支持多核、纠偏、可搜索 PDF；但依赖 Ghostscript 和 Tesseract，对 Windows VS Code 用户偏重 | 不做默认方案，可作为后续高级 PDF OCR |
| Tesseract | [tesseract-ocr/tesseract](https://github.com/tesseract-ocr/tesseract) | 老牌 OCR，支持 100+ 语言和多种输出格式；但需要系统二进制和语言包 | 不做默认方案，安装门槛高 |
| EasyOCR | [JaidedAI/EasyOCR](https://github.com/JaidedAI/EasyOCR) | API 简单，支持中文和英文；Windows 上需要先安装 torch/torchvision | 不适合当前轻便目标 |
| PaddleOCR | [PaddlePaddle/PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) | 功能强，支持 PDF/图片到结构化数据和 100+ 语言；依赖和能力范围都偏大 | 不做 0.1.9 默认方案 |
| client-ocr | [siva-sub/client-ocr](https://github.com/siva-sub/client-ocr) | 浏览器侧 ONNX OCR，支持 PDF/图片、本地处理；但项目较新，接入 Webview 会引入前端模型加载复杂度 | 暂不采用，仅记录为后续浏览器侧 OCR 方向 |

验收标准：

- 测试样本不包含真实个人隐私信息。

| 任务 | 说明 | 相关文件 |

验收标准：

- 同一测试样本下有明确的新旧包对比记录。
- 新包若被选中，关键字段命中不低于旧包。
- 新包若被选中，耗时不超过旧包 25%；若超过，需要保留旧包并记录原因。

## 5. 开发任务清单

### 5.1 任务一：改造 OCR 入口，支持 PDF 和图片

| 任务 | 说明 | 相关文件 |
|---|---|---|
| 输入类型识别 | 根据扩展名区分 `.pdf`、`.png`、`.jpg`、`.jpeg`、`.webp` | [resume_ocr.py](../../../agent/resume_ocr.py) |
| PDF 路径保留 | PDF 继续用 PyMuPDF 渲染页面后 OCR | [resume_ocr.py](../../../agent/resume_ocr.py) |
| 图片路径新增 | 图片直接传给 OCR 引擎或转为 numpy 数组识别 | [resume_ocr.py](../../../agent/resume_ocr.py) |
| 输出归一化 | 将 OCR 结果统一拼接为可注入面试上下文的纯文本 | [resume_ocr.py](../../../agent/resume_ocr.py) |
| 错误提示 | 不支持格式、依赖缺失、OCR 空结果分别给出清晰错误 | [resume_ocr.py](../../../agent/resume_ocr.py)、[webviewPanel.ts](../../../vscode-extension/src/webviewPanel.ts) |

验收标准：

- `python agent/resume_ocr.py sample.png` 可以输出文本。
- `python agent/resume_ocr.py sample.pdf` 可以输出文本。
- 不支持格式返回非 0，并输出可读错误。

### 5.2 任务二：RapidOCR 依赖与导入兼容

| 任务 | 说明 | 相关文件 |

验收标准：

- 新安装环境按 OCR 依赖清单能正常识别。

- 缺依赖时不会出现只有 Python traceback 的提示。

### 5.3 任务三：速度控制

| 任务 | 说明 | 相关文件 |
|---|---|---|
| OCR 引擎复用 | 单次 PDF 多页识别只初始化一次 OCR 引擎 | [resume_ocr.py](../../../agent/resume_ocr.py) |
| 页数限制 | 保留默认最多识别前 5 页，后续再按需要暴露配置 | [resume_ocr.py](../../../agent/resume_ocr.py) |
| 渲染分辨率控制 | 先固定 180-200 DPI 等效渲染，避免过高分辨率拖慢 | [resume_ocr.py](../../../agent/resume_ocr.py) |
| 超时保留 | VS Code Host 侧保留 OCR 子进程超时保护 | [webviewPanel.ts](../../../vscode-extension/src/webviewPanel.ts) |
| 耗时日志 | OCR 成功或失败时记录页数、文件类型、耗时到 Output Channel | [webviewPanel.ts](../../../vscode-extension/src/webviewPanel.ts) |

验收标准：

- 单页图片 warm run 目标耗时不超过 5 秒。
- 3 页扫描版 PDF warm run 目标耗时不超过 15 秒。
- 冷启动首次加载模型目标耗时不超过 30 秒。
- 超过目标时需要在任务结果中记录机器环境和实际耗时，不直接宣称通过。

### 5.4 任务四：质量控制

| 任务 | 说明 | 相关文件 |

验收标准：

- 清晰中文 + 英文图片样本关键字段命中率为 100%。

- 清晰样本字符召回率目标不低于 90%。
- OCR 空结果要提示“未识别到文字”，不能静默注入空简历。

### 7.2 手工验收

1. 安装 0.1.9 VSIX：

   ```powershell
   code --install-extension D:\project\interview-agent\vscode-extension\interview-agent-0.1.9.vsix --force
   ```

手工验收标准：

- PDF 和图片都可以通过 OCR 识别进入面试上下文。
- 普通文本类简历不受 OCR 依赖影响。
- OCR 失败时提示可读，不出现空白面板或长 traceback。
- OCR 处理超过超时阈值时能失败返回，不会卡死面板。

## 8. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| RapidOCR 新旧包 API 不兼容 | 迁移后 OCR 入口失败 | 先做新旧基准，再用兼容导入过渡 |
| OCR 依赖安装变慢 | 用户首次安装体验差 | 继续保持 OCR 可选依赖，只在扫描 PDF / 图片时提示 |
| 图片支持扩大上传面 | 误把非简历图片当简历 | 限制扩展名和大小，OCR 空结果时明确拒绝 |
| OCR 质量受扫描清晰度影响 | 简历上下文不完整 | 用关键字段命中测试兜底，并提示用户改用清晰文件或文本粘贴 |
| 速度目标受机器性能影响 | 验收结果不稳定 | 记录测试机器环境、冷启动 / warm run 耗时，按同机回归比较 |

## 9. 本版本改进建议

1. 0.1.9 先把 OCR 做成可测、可回归、可解释，不急着做复杂版面理解。
2. 优先迁移到 RapidOCR 当前主包，但必须用 PDF / 图片样本实测后再落地。
3. 图片简历支持要和 OCR 依赖提示绑定，避免普通用户误以为图片上传不需要额外依赖。

## 10. 下一个版本的优化建议

1. 继续修复系统文件资源管理器拖拽上传问题，并把 PDF、DOCX、TXT、MD、图片格式统一验收。
2. 优化 VSIX 体积，避免 OCR 或测试资源被错误打进基础扩展包。
3. 增加 OCR 处理进度反馈，例如当前页数、总页数和已耗时。

## 11. 后续可扩展的优化建议

1. 增加可搜索 PDF 生成能力，但只作为高级功能，不影响简历上传主流程。
