# Interview Agent 0.1.6 优化方案与任务清单

## 1. 本版本目标

0.1.6 包含一个阻塞性修复和三项既定优化：

1. **P0 修复**：解决用户点击「开始面试」时报 `内部错误: ModuleNotFoundError: No module named 'openai'`、完全无法使用真实 LLM 的问题。
2. **任务一**：重构 Python Agent 为异步可取消，让「停止」按钮真正中断生成。
3. **任务二**：引入 PDF、DOCX 解析依赖，简历附件支持 `.pdf / .docx / .txt / .md / .markdown`。
4. **任务三**：修复并实测「项目情况读取」，确保面试官能真正读到目标项目的技术栈，并借助内置面试题库提升追问深度。

产品定位不变：插件只做技术面试 Agent，不扩展为通用代码助手。

## 2. 用户反馈与问题拆解

| 序号 | 用户反馈 | 当前状态 | 0.1.6 处理方式 |
|---|---|---|---|
| 0 | 点击开始测试报 `内部错误: ModuleNotFoundError: No module named 'openai'` | 插件默认用系统 `python` 启动 Agent，系统 Python 未装 `openai` | 解释器自动探测 + 依赖预检 + 友好报错（P0） |
| 1 | 重构 Python Agent 为异步可取消 | `stop` 在 Python 侧是 no-op，主循环同步阻塞，UI 停止按钮只是本地状态切换 | 线程化 chat 处理 + 取消事件 + `cancelled` 协议通知 |
| 2 | 支持上传 PDF、Docx、txt、md 简历 | 只支持 `.txt / .md / .markdown`，PDF/DOCX 直接拒绝 | Node 侧引入 `pdf-parse` + `mammoth` 解析正文 |
| 3 | 实测项目读取是否满足面试官了解项目、深入提问 | `search_code` 被 `.venv`/`.git`/`.sessions` 等目录污染，20 条结果上限全是依赖库代码 | 搜索降噪（忽略目录）+ 内置面试题库 + 真机实测验收 |

## 3. 根因分析与现状调查（本轮实测结论）

### 3.1 P0：`openai` 报错根因（已复现确认）

报错传播链（每一环都已核对代码）：

```text
点击「开始面试」
→ Webview 发首轮 chat（含 JD + 简历）
→ TS 用 interview.pythonPath（默认 "python"，即系统 Python）spawn 子进程
→ init 正常（不触发 openai 导入）
→ chat → SessionStore._build_llm() → OpenAIClient.__init__()
→ 延迟导入 from openai import OpenAI  ← 此处抛 ModuleNotFoundError
→ main() 兜底捕获 → notify_error("内部错误: ModuleNotFoundError: ...")
```

环境实测证据：

```text
D:\project\interview-agent\.venv\Scripts\python.exe → openai 3.3.1 已安装 ✓
系统 PATH 里的 python（3.14.6）           → import openai 失败 ✗
```

结论：不是代码 bug，是**运行环境选择缺陷**——插件把「用哪个 Python」完全丢给了用户配置（默认系统 `python`），且对依赖缺失没有任何预检和可操作的提示。

### 3.2 「停止」现状：纯装饰

- TS 侧收到 stop 后转发给 Python；Python `_handle_stop` 是 no-op（`main.py` 明确注释是协议占位）。
- 更关键的是：`_handle_chat` 同步执行 `loop.run()`，**主循环阻塞期间 stdin 里的 stop 根本读不到**，等读到时本轮早已结束。
- Webview 点击停止只是本地 `setAwaiting(false)`；后台仍在生成，后续 `stream` 增量还会继续追加到气泡里，`done` 晚到再重置状态——行为割裂。

### 3.3 简历解析现状

`webviewPanel.ts` 的 `pickResume` 白名单只有 `.txt / .md / .markdown`，PDF/DOCX 直接报「请先转换为文本」。0.1.4 任务清单当时明确把 PDF/DOCX 解析列为暂缓事项，本版本补上。

### 3.4 项目读取现状：实测发现搜索污染（任务三的直接证据）

用当前仓库当工作区实测工具输出：

```text
search_code('redis')  → 20 处匹配（已截断），全部来自：
   .venv\Lib\site-packages\...（依赖库源码）
   .sessions\xlang-test.json（历史会话落盘，还泄漏了旧对话内容）
search_code('react')  → 20 处匹配全是 pygments 词法定义
```

根因：`SearchCodeTool.execute` 的 `os.walk` **没有任何忽略目录规则**；Windows 下 `.venv`、`.git` 等点号目录按字母序排在项目源码前面，20 条结果上限先被依赖库代码占满。`list_directory` 同样把 `.venv`、`.sessions` 等噪音目录原样列出。

结论：**当前版本面试官根本无法可靠读到目标项目的技术栈**——搜 "redis" 只会看到 pip 源码，看不到用户项目里真实的 Redis 用法。任务三必须先修搜索降噪，再谈提问深度。

另外：仓库内目前没有任何面试题库材料（已全局检索确认），「学习现有面试题」需要本版本新建。

## 4. 方案设计与取舍

### 4.1 P0 修复方案：解释器探测 + 依赖预检 + 友好报错

按优先级探测可用解释器，选中后做依赖预检：

```text
候选顺序：
1. interview.pythonPath（用户显式配置过、非默认值 "python" 时优先）
2. 目标工作区的 venv：{workspace}/.venv/Scripts/python.exe（Windows）
                       {workspace}/.venv/bin/python（macOS/Linux）
3. VS Code 的 python.defaultInterpreterPath 设置值（若已配置）
4. 兜底："python"（系统 PATH）

每个候选做预检：文件存在 + 能执行 `python -c "import openai"`，
第一个通过的胜出；全部失败 → 给出可操作的错误提示。
```

配套改动：

- **Python 侧兜底**：`OpenAIClient.__init__` 捕获 `ModuleNotFoundError`，抛带操作指引的 `LLMError`，不再以「内部错误」面目示人。
- **探测日志**：最终选用哪个解释器写入 `Interview Agent` 输出通道，方便排查。
- **错误提示文案**（全部失败时）：

```text
未找到已安装 openai 依赖的 Python 环境。
解决方法任选其一：
1. 在设置 interview.pythonPath 里填写目标项目 venv 的 python 完整路径
2. 用当前解释器执行：pip install openai
3. 勾选 Demo Mode 体验完整流程（不需要 API 和依赖）
```

- 打包时随 `bundled-agent` 附带 `requirements-agent.txt`，提示文案可引用。

不做（保持暂缓）：自动创建 venv、自动 pip install——涉及网络与磁盘写入，放到后续版本评估。

### 4.2 任务一方案：线程 + 取消事件（不引入 asyncio 全家桶）

对比过两条路：

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 线程化（推荐） | 主线程继续读 stdin，chat 提交到单独工作线程执行；`threading.Event` 作取消信号 | 改动小：`AgentLoop.run`/`LLMClient.chat` 保持同步接口；LLM 调用是 I/O 密集，GIL 不构成瓶颈；Windows 下 stdin 无兼容性问题 |
| B. asyncio 重写 | `AsyncOpenAI` + asyncio 流式读 stdin | 需要重写 AgentLoop、LLMClient 协议和全部相关测试；Windows 下 asyncio 读 stdin 还需线程桥接；收益与成本不成比例 |

方案 A 设计要点：

```text
主线程：for line in stdin → 分发
  chat  → 提交工作线程（同一时间只允许一轮；运行中来新 chat → error「请先停止当前回答」）
  stop  → set 取消事件
  init  → 照旧（仅允许在空闲时执行，运行中先取消再配置？——不允许，报错提示）

工作线程：loop.run(text, should_cancel=event.is_set)
  取消检查点：
  ① 每个 Agent step 之前（调 LLM 前）
  ② 每次工具调用之前
  ③ 流式期间每个 chunk（llm_client._chat_streaming 里逐块检查）
  命中 → 抛 AgentCancelled 异常 → 已生成的部分文本照常入历史（与设计 6.5「中断保留」一致）
  → notify("cancelled", {session, partial}) 

协议：新增通知 method = "cancelled"（Python protocol.py / TS protocol.ts / Webview main.js 三处对齐）
```

### 4.3 任务二方案：Node 侧解析（不放 Python 侧）

| 方案 | 取舍 |
|---|---|
| Node 侧 `pdf-parse` + `mammoth`（推荐） | 依赖打进 VSIX 随插件分发，用户零配置；和现有 `pickResume` 读取流程无缝衔接 |
| Python 侧 `pypdf` + `python-docx` | 加重刚在 P0 里修的解释器依赖问题（用户环境更难装齐），否决 |

要点：

- `mammoth.extractRawText()` 抽 DOCX 纯文本；`pdf-parse` 抽 PDF 文本（注意其入口文件在 `module.parent` 为空时会走 debug 分支，需直接引 `pdf-parse/lib/pdf-parse.js` 规避）。
- 解析在 Extension Host 做（异步），抽出文本后走现有 `resumePicked` 消息进 Webview，80,000 字截断逻辑复用。
- 扫描版 PDF（无文字层）抽不出文本 → 报 `resumeError`，提示改用文本粘贴。
- VSIX 体积增加约 2–3 MB，可接受。

### 4.4 任务三方案：搜索降噪 + 内置面试题库

**先说清「学习现有的面试题」的实现口径**：不是对模型做微调训练，而是**知识注入**——内置一份精选题库，让面试官在锁定某技术点后能按「原理 / 权衡 / 实践」的结构化路径深入追问。分两层：

1. **搜索降噪（修复，必做）**：`SearchCodeTool` / `ListDirectoryTool` 增加忽略目录集：

```text
IGNORED_DIRS = {".git", ".venv", "venv", "env", "node_modules", "dist",
                "build", "out", "target", "__pycache__", ".pytest_cache",
                ".ruff_cache", ".sessions", ".idea", ".vscode", ".next",
                "coverage"}
```

   `os.walk` 剪枝跳过这些目录；`list_directory` 同样过滤，降低面试官被噪音带偏的概率。

2. **面试题库（增强，必做）**：新增 `agent/resources/question_bank.py`（或 JSON）+ 新工具 `lookup_questions`：

```text
题库结构（精选 10–15 个核心技术主题，每主题 3–5 道深度问题，覆盖：
Redis、MySQL、并发/线程、Flask/FastAPI、React/Vue、消息队列、
Docker、网络 HTTP/TCP、JWT/鉴权、异步 IO 等）

面试官工作流：search_code 锁定技术点 → lookup_questions(tech="redis")
→ 按返回的题目路径逐层深入追问

用工具按需拉取而不是整包塞进系统提示，避免系统提示膨胀。
```

3. **系统提示微调**：`INTERVIEWER_SYSTEM_PROMPT` 的「工作流程」段补充一句：锁定技术点后可调 `lookup_questions` 获取该技术的深度追问路径。

4. **真机实测（验收动作，不是新代码）**：在本仓库上以 Demo Mode + 真实 API 各跑一轮完整面试，核对面试官的工具调用与提问是否真的基于项目实际技术（而不是依赖库代码或通用八股）。

## 7. 0.1.6 验收步骤与验收标准

验收步骤：

1. 卸载旧版插件，关闭所有 VS Code 窗口后重开。
2. 从 `interview-agent-0.1.6.vsix` 安装，执行 `Developer: Reload Window`。
3. 打开一个目标项目文件夹（推荐先拿本仓库或一个带 `.venv` 的项目测 P0）。
4. 不改任何设置，直接填 JD、上传简历，点击「开始面试」。

验收标准：

**P0 环境修复**

- 真实模式下不再出现 `ModuleNotFoundError: No module named 'openai'`。
- 工作区有 `.venv`（装了 openai）时无需配置 `interview.pythonPath` 即可用。
- 依赖全缺失时出现三条解决指引，Demo Mode 仍可正常体验。

**异步可取消**

- 生成中点停止：文字立刻停，气泡标记「已停止」，可继续对话。
- 停止后发送新消息，上下文包含被中断轮的部分内容。

**简历解析**

- `.pdf`、`.docx`、`.txt`、`.md` 四种简历都能上传并进入面试上下文。

**项目读取与提问深度**

- 聊天区工具气泡里 `search_code` 的结果不再出现 `.venv`、`node_modules` 路径。
- 面试官追问的技术点与项目实际使用的技术一致；追问有「原理/权衡/实践」层次感。

## 8. 暂缓事项

## 9. 本版本改进建议

对本任务清单方案本身的补充建议：

1. **任务 0 与任务一有耦合点**：异步改造后 Agent 进程生命周期变长，解释器探测建议在「首次启动 Agent」时只做一次并缓存结果，避免每轮 chat 都探测。
2. **任务三题库先小后大**：首版题库控制在 10–15 个主题即可，宁可每个主题的题目质量高，也不要铺 50 个主题的浅题。建议每道题都带「考察点说明」，面试官提示里注明可以按考察点改述题目，避免生硬照念。
3. **`pdf-parse` 的引入有已知坑**（`module.parent` 为空时走 debug 分支），实现时直接引 `pdf-parse/lib/pdf-parse.js`；若仍有问题可换 `pdfjs-dist`，任务清单里应允许实现时二选一。
4. **`cancelled` 通知建议带 `partial` 字段**（已生成文本摘要），前端展示「已停止（生成 N 字）」，对用户更友好。

## 10. 下一个版本的优化建议

0.1.6 完成后的下一个版本（0.1.7）建议方向：

1. **依赖自动安装**：P0 只做探测和指引，0.1.7 可做「一键安装依赖」按钮（终端里执行 `pip install -r requirements-agent.txt`），彻底消除环境配置门槛。
2. **面试报告**：面试结束后生成结构化报告（薄弱点清单 + 每个技术点的评语 + 复习建议），可导出 Markdown。这是面试闭环的自然终点。
3. **历史会话管理 UI**：`.sessions` 已有落盘能力，补一个「继续上次面试 / 新面试」入口，让跨窗口续接可见。

## 11. 后续可扩展的优化建议

长期可规划的方向：

1. **题库规模化与 RAG**：题库扩展到上百主题后，全量塞工具结果不现实，可引入轻量检索（按 JD 关键词 + 项目技术栈预筛主题）。
2. **多轮面试编排**：按 JD 自动生成面试大纲（技术点优先级排序、每点追问深度预算），模拟真实面试的节奏控制。
3. **代码理解深化**：引入 tree-sitter 做符号级检索（搜「类/函数」而不是「文本行」），让面试官的提问能落到具体实现上。
4. **回答质量评估**：对每个回答打分（1–5）并沉淀到面试报告，量化求职者的薄弱分布。
5. **Webview 体验**：工具气泡可折叠、面试官消息支持 Markdown 渲染（表格/代码块高亮）。
